# FACTORY: the CoolHackers delivery line

Five Band seats, one room, one dispatch per stage. This page covers:

- how the factory is built;
- why it is built that way;
- what broke on the way;
- what the run cost;
- how the factory stops a wrong result from shipping.

The factory's source is in the team repository
(https://github.com/June24-optimize/Hercules-coolhackers). The mandates there are generated by
`tools/build_mandates.py`; the copies in `mandates/` here are byte-identical.

## Seats

| Seat | Harness | Model | Owns |
|---|---|---|---|
| coordinator | Claude Code | claude-sonnet-5 (Claude subscription) | Requirements, design and ADRs, task list, routing every handoff, stage report |
| tester | OpenCode | GLM-5.3-Flash via Featherless | Completeness review of the requirements, then a black-box acceptance suite written from the spec only |
| developer | OpenCode | GLM-5.3-Flash via Featherless | Implements tasks test-first in its own worktree, one commit per task |
| reviewer | Claude Code | claude-sonnet-5 (Claude subscription) | Independent review of each batch from a fresh worktree; **the only seat that merges to `main`**; stage verification |
| timekeeper | Band CLI script | none | Sends `@coordinator` a clock tick every 15 minutes while a stage runs |

The split is deliberate. The two seats whose judgement decides what ships, the coordinator and
the reviewer, run the stronger model. The two seats that produce the volume (code and tests) run
a cheap per-token model. Implementation is about 80% of the tokens, so most of the work runs at
Featherless prices.

## Setup (how another team stands it up)

1. Create an empty result repo with a neutral repo-level git identity (`unattributed-seat`).
   Every seat commits under its own name via `git -c user.name=<seat>`. A commit that forgets to
   do so shows up as `unattributed-seat`, never as a human.
2. Run `setup-seats.sh`. It reads each mandate's `Harness:`/`Model:` lines and creates the seat
   with `band agent create`, live-linked to the mandate:
   - Claude Code seats use the `claude-code-cli` transport with the subscription login.
   - OpenCode seats use the `opencode` transport through `tools/opencode-featherless`, which
     hands them the Featherless key from launchd. Band's background service doesn't read
     shell profiles.
3. Permissions are pre-allowed, so no seat stalls on a prompt: `claude-settings.json` and
   `opencode-seats.json`. Both deny `git push` and `sudo`, and both make the kickoff package's
   test files and harness source unreadable. The OpenCode config also caps tool output
   (300 lines / 16 KB) and compacts early, to keep contexts and cost small.
4. For each stage, `tools/start-stage.sh N <room>` runs these checks:
   - Featherless key, Claude login, Docker;
   - the mandate scan;
   - the team repo is committed;
   - the result repo's identity;
   - all five seats connected.
   It then starts the timekeeper and puts that stage's dispatch on the clipboard. The human
   pastes it and posts nothing else.

## How a stage flows

```
dispatch ─► coordinator: carry forward ─► requirements ─► design/ADRs ─► tasks (3–5 review batches)
                │                           ▲
                │                  tester: completeness review
                ├─► developer: tasks, test-first, commit per task ─► batch handoff ─► reviewer
                └─► tester: acceptance suite from the spec ─────────► merge request ─► reviewer
reviewer: fresh worktree at the exact SHA, unit + acceptance + probes ─► accept & merge | reject
all batches + suite merged ─► reviewer: stage verification (fresh clone, docker build --no-cache,
harness isolated run, invariant stress probe) ─► coordinator: report.md ─► stop
```

Key rules in the mandates, each one added after we watched it fail (see below):

- **Messages are actions.** Only the send tool delivers a message; a turn's final text is never
  seen. Mention only the seat that must act, and hand off directly to it. Merge and verify
  requests go to `@reviewer`, not through the coordinator.
- **A rejection takes priority over everything.** The coordinator routes it as the developer's
  next task, ahead of all others.
- **Waiting has a clock.** Seats have no timer, so they check `date`. After 15 minutes with no
  reply they resend once, identically; after that they raise a blocker.
- **The reviewer reviews the exact SHA it was given**, not the branch tip. The developer keeps
  working ahead, and reviewing the tip would overshoot.
- **Generic mandates.** The mandates say how the factory works and name no track vocabulary.
  Everything about Pocketful is in the dispatch.

## How the factory catches a bad result

- **Spec before code.** The tester reviews the coordinator's requirements for completeness
  before work starts (stage 1: 13 findings; stage 2: 8 findings). The coordinator amends the
  requirements before any code is written.
- **Two independent test sources.** The developer writes unit tests from the design. The
  tester writes a black-box HTTP acceptance suite from the requirements only; it never sees the
  code first, and no seat may read the supplied tests. A defect has to slip past both.
- **One merger.** Only the reviewer merges. It merges after re-running everything itself in a
  fresh worktree, so a seat's "green" report is never trusted on its own.
- **Money invariants are probed, not assumed.** At each stage verification the reviewer runs
  its own concurrent stress probe, recorded in `specs/stage-N/probes/`. Stage 4 sent a burst
  of 50 mixed requests in flight and checked:
  - conservation: 1,500,100 in = 1,500,100 out;
  - no negative total, available or held balance;
  - 20 concurrent payments with the same idempotency key → exactly one creation;
  - a batch with one stale item → rejected all-or-nothing.
- **Real rejections happened.** Each was routed back and fixed:
  - stage 2: payment IDs missing from authorization responses; wrong status code for a
    non-boolean field;
  - stage 3: a correction mutated the stored original response; `GET /me` and `GET /statement`
    were inconsistent;
  - stage 4: the batch endpoint checked the refund floor before staleness.
  The reviewer also caught a tester "green" report that had been run against a locally rebased
  branch rather than `main`, which would have been a false pass.
- **Verification is the judges' own check.** Every stage ends with
  `harness run --mode isolated` on a fresh clone with a no-cache build. Each stage claims
  exactly its own number and doesn't overshoot.

## Measured cost and time

| | Stage 1 | Stage 2 | Stage 3 | Stage 4 |
|---|---|---|---|---|
| Dispatch → report (CEST) | 16:16 → 20:26 | 20:38 → 02:59 | 04:09 → 09:39 | 12:44 → 17:45 |
| Wall-clock | 4h 10m | 6h 21m | 5h 30m | 5h 01m |

Total: about 21 hours of wall-clock time for four stages and 132 seat commits (coordinator 26,
developer 78, reviewer 8, tester 19, plus one unattributed merge; see below).

- **Claude seats (coordinator and reviewer)**, from `band usage rooms`:
  - first room: 329.8M tokens;
  - continuation room: 28.8M tokens;
  - total: about 358.6M tokens, mostly cache reads.

  That is about $96 at list prices, but it was paid by a Claude subscription, so the marginal
  cost was $0.
- **Featherless (tester and developer, GLM-5.3-Flash)**: **about $10.50 for the whole run.**
  - The Featherless dashboard bills **$13.82 for 29 Sep–1 Oct** (1,496 billed requests). That
    period also covers our last practice run, so the judged run cost at most $13.82.
  - OpenCode's per-request token log puts **76% of that period's tokens in the judged run**,
    which gives about $10.50.
  - OpenCode logs model turns, which do not map one-to-one onto billed requests. Almost all
    input was billed at the cached rate. A list-price calculation at $0.15 per
    million input tokens would have overstated the cost about fourfold.

  | | Stage 1 | Stage 2 | Stage 3 | Stage 4 | Total |
  |---|---|---|---|---|---|
  | Model turns (OpenCode log) | 347 | 633 | 484 | 468 | 1,932 |
  | Input tokens (incl. cached) | 55.2M | 125.9M | 101.5M | 56.8M | 339.4M |
  | Output tokens | 0.29M | 0.39M | 0.41M | 0.32M | 1.40M |
  | Cost (by token share) | ≈ $1.71 | ≈ $3.89 | ≈ $3.14 | ≈ $1.76 | ≈ $10.50 |

  - **Stage 2 cost the most.** It was the longest stage with the most requests, including
    about 3 hours in which a rejection went unseen and work continued on top of it. The
    "rejection first" rule came out of that.
  - **Output is under 1% of the tokens.** The bill is almost all context re-reading, which is
    why the OpenCode config caps tool output and compacts early.
- **Rehearsals before the judged run:** a toy run and two Pocketful practice runs, archived
  separately. The practice runs on 29–30 Sep cost about $3.30 on Featherless (the dashboard
  period minus the judged run). The toy run on 28 Sep falls before that period.

Wall-clock time includes waits that were not work:

- Claude subscription usage limits: stages 2 and 3 each paused until the limit reset, and the
  timekeeper resumed them unattended (21:37 and 07:23).
- The room-limit outage in stage 4 (below).

## Human input, all of it

Everything a human posted in the rooms:

| When (CEST) | Room | Message |
|---|---|---|
| 30 Sep 16:16 | 1 | Stage 1 dispatch |
| 30 Sep 20:20 | 1 | **Nudge:** "the tester's suite tester-stage1@066bb54 awaits your merge, then run stage verification" |
| 30 Sep 20:38 | 1 | Stage 2 dispatch |
| 1 Oct 04:09 | 1 | Stage 3 dispatch |
| 1 Oct 12:44 | 1 | Stage 4 dispatch |
| 1 Oct ~16:18 | 2 | Stage 4 recovery message (platform limit, below) |

- **The stage-1 nudge** is our one real intervention. The tester sent its merge request to the
  coordinator instead of the reviewer, the coordinator assumed the reviewer had it, and the band
  stalled for an hour. The fix is in the mandates (hand off directly to the acting seat) and in
  the timekeeper. No stage after that needed a nudge.
- **The recovery message** is not steering.
  - At 14:01 CEST, the first room reached Band's limit of 10,000 messages per room, which
    counts tool calls and thoughts. After that, Band rejected every send with HTTP 403
    `limit_reached`. The seats kept working, but no handoff could be delivered.
  - Our plan offered no upgrade, and deleting messages would have destroyed the log. So we
    opened a continuation room with the same five seats and posted one message.
  - That message stated the outage, the last delivered state (branch tips, which merges were
    pending), and the original stage-4 dispatch unchanged. It told the coordinator to rebuild
    its state from the git repository.
  - It finished stage 4 from there unattended. That's why there are two room files:
    `room.json` (stages 1–4 up to 14:01) and `room-2.json` (the rest of stage 4).

**About the two room files.** Both are Band's "Download full session" files:

- `room.json` has 10,000 messages. Its only edit is the one the participant guide allows: six
  bearer tokens are replaced with `[REDACTED]` (34 occurrences). They were session tokens that
  the Pocketful service under test issued to the seats' HTTP probes on `127.0.0.1`, and they
  expired with those throwaway containers.
- `room-2.json` has 1,065 messages and is unchanged. `harness check` reports a
  `NAME=value` env-assignment in it. That rule is skipped only for a file named exactly
  `room.json`, and the matches are code inside tool calls (`token = …`,
  `password = require_string(…)`, idempotency `key = …`). We checked every one; none is a
  credential.

## What we tried that failed, and what changed

| Attempt | What went wrong | Change |
|---|---|---|
| Nine seats (original design) | Three seats in a practice run used about half the Featherless credit, mostly on coordination messages | Four model seats; fewer, larger messages; mention only the seat that must act |
| All seats on OpenCode + Featherless | The coordinator reasoned for minutes without acting; one runaway 32k-token reasoning turn | Coordinator and reviewer moved to Claude Code |
| Plain final text as a reply | Band delivers only send-tool messages; the reviewer's verdict was never seen | "Messages are actions" rule |
| Reviewing the branch tip | The developer had already pushed ahead, so the review covered unrequested work | Review the exact SHA in the handoff |
| Developer ignored a rejection while finishing the next batch | The rejection sat for ~3h in stage 2 | "A rejection takes priority over everything" |
| Relying on seats to notice a stall | Seats only act when a message arrives, and they have no timer | The timekeeper seat, plus the 15-minute resend rule |
| Merge commits with the human's git identity (practice run) | Would read as human-written code | Explicit `-c user.name=` on merges, plus the neutral repo identity |
| One room for the whole run | Hit Band's 10,000-message cap in stage 4 | Continuation room (above). Next time, start a fresh room per stage |

**The one unattributed commit:** `d7697a4` is the tester merging the coordinator's docs branch
into its own branch with a plain `git merge`. The neutral repo identity recorded it as
`unattributed-seat` instead of the human's name, which is exactly the safety net working.
